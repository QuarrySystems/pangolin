### Findings

- **BLOCKING** · §6's regression guard is scoped to the one case that will not regress; the case that *will* regress — a config file that **exists** — has no stated requirement and no stated test.
  - Artifact text: "**Regression guard.** `pangolin subagent sync --provider claude-code --dry-run` works today in a repo with no config at all, because `--dry-run` skips the client entirely (`cmd-subagent.ts:125`, `cmd-capabilities.ts:60`). If `getSyncProviders` threw on a missing config file, that would break. §8 covers it with a test." And D6: "Missing config file or missing export yields `[]`, never an error."
  - Evidence: today `--dry-run` sync **never imports the config**: `cmd-subagent.ts:125` is `const client = opts.dryRun ? null : await ctx.getClient()`, and `getClient` is the only thing that imports it (`index.ts:46-69`). After the change, §4.3 puts `await ctx.getSyncProviders()` ahead of `resolveProvider`, which is the *first* statement of both actions (`cmd-subagent.ts:122`, `cmd-capabilities.ts:57`), and §7's `loadConfigModule` imports the config module to read the export. So **every** sync invocation, dry-run included, now executes the config's module body. That body is not inert: `examples/offload-fanout/pangolin.config.mjs:63` opens a SQLite file and `:66` registers a `process.on('exit')` hook; `deploy/serve-stack/pangolin.config.mjs:52-60` constructs an S3 client; `docs-site/src/content/docs/reference/config.md:80-81` documents import-safety as a property configs must be *written* to have, not one they get for free. D6 enumerates exactly two cases ("missing config file or missing export") and is silent on the third: the config exists and throws at import.
  - Concrete failure: in a repo whose `pangolin.config.mjs` throws at load (missing required env, unreadable seed file, S3 endpoint parse), `pangolin capabilities sync --provider claude-code --dry-run` — documented as a no-writes preview at `docs-site/.../how-to/sync-capabilities-subagents.md:35` — now fails with a config-load error instead of printing. Even when the import succeeds, a pure parse-and-print acquires the config's side effects (a `.db` file, an exit hook). The §9 row that claims to guard this ("no config file → `[]`, and `--dry-run` sync on a built-in still succeeds") is green throughout, because it exercises the *absent*-config path.
  - Resolution: the author must choose and state one — **(A)** D6 gains a third clause ("a config file that throws at import yields `[]` for `syncProviders`, with the error surfaced only when a config-supplied provider is actually named"), plus a §9 row "config file present and throwing at import → `--dry-run` sync on a built-in still succeeds, and still prints `(dry-run) subagent <n>`"; or **(B)** state explicitly that dry-run sync now loads the config, accept the behavior change, and add the §9 row asserting the config module body *is* evaluated so the change is at least pinned. Either way the guard row must be re-scoped to a present-config fixture and must carry the positive companion the existing test already uses (`cmd-subagent.test.ts:121`), because "succeeds" alone passes on a zero-file source dir.

- **DEFERRED** · §5 and §6 give contradictory answers for `syncProviders === undefined`, and §9 lists both conflicting tests as if they coexist.
  - Artifact text: §5 — "Rejects: a non-array export; …" and §9 — "Validation | non-array export rejected, naming the config file". - **DEFERRED** · The two merge-time error messages are unassertable as specified: "naming both" is under-determined, and `mergeProviders` structurally cannot name the config file the way §5's validator errors do.
  - Artifact text: §9 — "Merge | collision with a built-in throws, naming both"; §4.2 — "Two error cases, both thrown at merge time"; §5 — "Errors name the config file and the offending array index."
