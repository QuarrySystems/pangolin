### Findings

- **BLOCKING** · The spec enumerates exactly two non-error config outcomes and is silent on the third — *config file present, import throws* — which this change makes newly reachable on a path that touches no config today.
  - Artifact text: D6 — "Missing config file or missing export yields `[]`, never an error". §6 — "**Regression guard.** `pangolin subagent sync --provider claude-code --dry-run` works today in a repo with no config at all, because `--dry-run` skips the client entirely (`cmd-subagent.ts:125`, `cmd-capabilities.ts:60`). If `getSyncProviders` threw on a missing config file, that would break."
  - Evidence: §4.3 places `await ctx.getSyncProviders()` before `resolveProvider`, which is the first statement of both actions (`packages/pangolin-cli/src/cmd-subagent.ts:122`, `cmd-capabilities.ts:57`) — i.e. *unconditionally*, ahead of the dry-run branch at `cmd-subagent.ts:125` / `cmd-capabilities.ts:60`. Today the config is imported only inside `defaultGetClient` (`src/index.ts:59`), so dry-run does zero config I/O — an invariant two existing tests assert (`test/cmd-subagent.test.ts:120`, `test/cmd-capabilities.test.ts:66`). The import-throw case is reachable: `pangolin.config.ts` is the first resolution candidate (`src/index.ts:52`, documented first at `docs-site/src/content/docs/reference/config.md:18`) and `await import()` of a `.ts` file needs a type-stripping runtime; and configs import third-party packages at module scope (`deploy/serve-stack/pangolin.config.mjs:25-46`), which throw `ERR_MODULE_NOT_FOUND` when resolved from a cwd that lacks them. The in-repo configs carry a hand-maintained "IMPORT-SAFE" comment (`examples/offload-minio/pangolin.config.mjs:7`, `deploy/serve-stack/pangolin.config.mjs:6`) — a convention, not a mechanism, and one no external config is bound by.
  - Concrete failure: the spec picks neither branch and both are damaging. (a) *Propagate* — the natural reading, since D6 excuses only two cases — and `pangolin subagent sync --provider claude-code --dry-run`, which works today in **any** repo, now fails in every repo whose config is not import-clean. §9's only absent-config row uses "no config file", so the suite will be green. (b) *Swallow* → `[]` and a config with a syntax error degrades silently to `unknown --provider remora (known: claude-code, stoa)` — exactly the illegible support-thread failure D3 was written to prevent. Separately, §6's stated blast radius is understated: it frames the regression surface as "a repo with no config at all", when the change actually makes **every** sync invocation, dry-run included, depend on the config module evaluating cleanly.
  - Resolution: undecidable as written — the author must choose between (A) `getSyncProviders` propagates import errors, and §6's guard is widened to "config present and import-hostile" with a test; and (B) it degrades to `[]` on import failure but emits a warning naming the file and the underlying error, so the misleading unknown-provider message cannot occur silently.

- **DEFERRED** · A malformed or colliding third-party provider entry aborts sync invocations that name a built-in and depend on no config provider; the spec never states this.
  - Artifact text: §4.2 — "Two error cases, both thrown at merge time". §4.3 — "Both delegate to `mergeProviders`." §6 — "Sync verbs run fine on built-ins alone."
  - Evidence: `resolveProvider` is the single gate for both actions (`cmd-subagent.ts:122`, `cmd-capabilities.ts:57`), so any throw from `mergeProviders`/`validateSyncProviders` aborts the action before `--provider` is even consulted. §9's merge/validation rows assert only that the throws happen; no row asserts that a built-in still resolves when an unrelated config entry is bad.
  - Concrete failure: an operator running `pangolin capabilities sync --provider claude-code` — a path with zero dependence on config providers — is blocked by a duplicate-name or shape error in a `syncProviders` entry they may not own, with no flag to bypass it. This silently contradicts §6's stated principle.
  - Resolution: state the intent explicitly — either "any bad config provider fails all sync verbs, by design" (and add a test pinning it), or scope validation/merge failure to the requested name.

- **DEFERRED** · `CliContext` gains a third member with no statement of whether it is optional and no account of existing constructors.
  - Artifact text: "`CliContext` (`index.ts:23-30`) gains a third seam beside the two that exist: `getSyncProviders: () => Promise<SyncProvider[]>;`" — written non-optional, with no migration note.
  - Evidence: existing call sites pass `{ getClient }` only (`test/cmd-subagent.test.ts:114`, `test/cmd-capabilities.test.ts:60`, `test/bin-entry.test.ts:5`), and tests are excluded from typechecking (`packages/pangolin-cli/tsconfig.json` `include: ["src/**/*"]`), so this surfaces as a runtime `TypeError: ctx.getSyncProviders is not a function` rather than a compile error. `CliContext` is a published root export (`src/index.ts:23`) and `buildProgram(ctx)` is public (`:32`), so external embedders break too.
  - Concrete failure: the two tests that break are precisely the two dry-run guards §6 leans on — the implementer must repair the regression guard in the same change that creates the regression risk, which is how a guard quietly gets loosened instead of extended. §8's semver posture is scoped to the SPI and says nothing about the root `CliContext`.
  - Resolution: declare the member optional (`getSyncProviders?`) with a `?? []` fallback at the two call sites, or state that all `CliContext` constructors are updated and that this is a breaking change to the root surface.

- **DEFERRED** · The spec never states that `pangolin.config` is also imported by `pangolin-mcp`, so the blast radius of a `syncProviders` export is described as CLI-only when it is not.
  - Artifact text: §1.4 — "`pangolin.config` already executes arbitrary code with full credentials **at CLI time**"; "providers never become reachable from `pangolin-mcp` or a dispatched worker". D8 — "The **three** config-resolution copies collapse to one helper".
  - Evidence: `packages/pangolin-mcp/src/bin.ts:21-28` runs the identical `['pangolin.config.ts','pangolin.config.js','pangolin.config.mjs']` probe against cwd and `await import()`s the whole module; it reads only `mod.default ?? mod.client` (`:29`) and `mod.orch` (`:41`), but module evaluation is unconditional. Any rejection exits the process (`:53-57`). Both ends checked: producer = the §4.1 config example `export const syncProviders = [new RemoraProvider()]`; consumer = `bin.ts:28`.
  - Concrete failure: the endorsed registration form runs a third-party package's module init and constructor inside the `pangolin-mcp` process at startup. If `remora-pangolin-provider` is not resolvable from the cwd the MCP server runs in, or its constructor throws, `pangolin-mcp` fails to start — a surface §1.4 asserts is untouched. D5's validator never runs there. (Not a privilege escalation: ADR-0005's enforcement is the tool-name allowlist, `0005-…md:71-79`, and that is genuinely unaffected — "reachable" in the ADR sense stays false.)
  - Resolution: state that `pangolin-mcp` ignores `syncProviders` but shares the module, record the startup coupling as a documented consequence, and correct D8's copy count (the third copy lives in a different package).

### Checked, no finding

- **Provider output is guarded downstream.** D5 validates provider *shape*, not *output*, and the spec does not say what happens when an out-of-tree provider emits junk — but the register boundary already catches the realistic cases: a `SubagentDef` with neither prompt field throws (`pangolin-client/src/subagent-register.ts:59-63`), an empty/`/`-bearing name is rejected by `assertSegment` (`pangolin-core/src/uri.ts:106`), and bundles are size-capped and credential-scanned (`pangolin-client/src/capabilities-register.ts:39,71-80`). Loud failures, not silent corruption. No absence to report.
- **Arbitrary bundle keys are not a new hazard.** §11's dismissal of the "capability bundle path seam" holds even for untrusted providers: an out-of-tree provider can emit `pangolin-setup.sh` (executed by the worker, `pangolin-worker/src/setup-script.ts:55`), but the same operator can already do that today via `pangolin capabilities register --from <dir>`, whose keys are plain `relative()` paths (`cmd-capabilities.ts:86`). No new capability, so no unstated guard is missing.
- **Idempotency / replay of a repeated sync.** Both registers are content-hash idempotent (`subagent-register.ts:97-101`; `capabilities-register.ts:19-23`), so the spec's silence on double-firing is correct silence.
- **Empty and boundary inputs on the new export.** `syncProviders = []` collapses cleanly into D6's semantics; a non-array, a non-object entry, and a missing method are all in §5's stated rejection list; `mergeProviders` with zero extras is the current behavior.
- **Ordering / tie-breaking.** The enumeration in the unknown-provider error (§4.3) has a unique, deterministic key — `Map` insertion order, built-ins first (`providers/index.ts:11-14`) — so no tie-break rule is missing.
- **The `exports`-map blast radius (§3) is accurately stated, not understated.** Verified two ways (see grounding table); `bin` resolution is by file path and unaffected, and `test/scaffold-shape.test.ts:23-61` asserts no exhaustive package.json key set that adding `exports` would trip. The only casualty is a *comment* at `examples/manifest/test/deploy.test.ts:26` recommending the `dist/` deep-import workaround, which the map forecloses — stale text, not a break.
- **Timezone/date and concurrency.** Nothing in this change crosses a date boundary, and `runSync` is a sequential single-process loop (`src/sync.ts:26-33`); cross-operator concurrency on the same catalog is pre-existing and unchanged by the SPI.
