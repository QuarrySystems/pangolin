### Findings

- **DEFERRED** · D8's consolidation misses the fourth copy of the config loader, and the helper as specified is private, so no shared import path will exist after the change either.
  - Artifact text: "`getSyncProviders` would be the third copy, which is where duplication becomes the pattern." … "One helper, callers keep their own semantics: `async function loadConfigModule(): Promise<…>`"
  - Evidence: the identical filename triple + `access` probe + `pathToFileURL` dynamic import exists in **three** places today — `packages/pangolin-cli/src/index.ts:52`, `packages/pangolin-cli/src/index.ts:77`, and `packages/pangolin-mcp/src/bin.ts:21` (whose own header comment at `:4` says "mirroring pangolin-cli's pattern"). The mcp copy is byte-for-byte the same loop with only the error prefix changed (`bin.ts:32`, `:48` vs `index.ts:63`, `:68`). No shared path exists: `packages/pangolin-mcp/package.json:35-40` does not list `@quarry-systems/pangolin-cli`, and a grep of `packages/pangolin-mcp/**` for `pangolin-cli` returns only comments. §7 writes the helper without `export`, so even a future dependency edge could not reach it.
  - Concrete failure: `docs-site/src/content/docs/reference/config.md:8-23` documents one resolution order for "The `pangolin` CLI **and the MCP server**". After this change that order is asserted in two independent places with no compile-time link. Adding `pangolin.config.mts`, reordering `.js` before `.ts`, or switching to an upward directory walk lands in the CLI helper; `pangolin-mcp` silently keeps the old behavior and the two binaries resolve different config files in the same repo. This is drift, not a crash — hence DEFERRED, not BLOCKING.
  - Resolution: undecidable as written — the author must choose between (a) `export` the helper and let `pangolin-mcp` depend on `pangolin-cli`, which adds a package-graph edge `package-map.md:38-43` does not show and inverts the "cli and mcp are both leaf consumers of client" shape (worse coupling than a third copy, in my read); (b) place the loader in a package both already depend on — `pangolin-client` is the only candidate, since `pangolin-core` is declared types-only (`package-map.md:9-10`); or (c) **note the divergence deliberately** — correct D8's count to "two of the three copies, in-package only", and add a one-line pointer in `pangolin-mcp/src/bin.ts` and in `config.md` that the two loaders must be changed together. Given the coupling cost of (a) and (b), (c) is the cheap honest answer, but the spec should say so rather than leave the count wrong.

- **DEFERRED** · The module being published as the provisional SPI (`./providers`) is simultaneously the internal registry, the collision-policy owner, and (by implication) the validator's home — so CLI plumbing becomes public API by placement accident, and the SPI's boundary is never delimited.
  - Artifact text: D1 "Publish a provider-authoring SPI at the `./providers` subpath"; §3 `"./providers": { "types": "./dist/providers/index.d.ts", "default": "./dist/providers/index.js" }`; §4.2 "A new pure function in `providers/index.ts`: `export function mergeProviders(...)`"; §5 `export function validateSyncProviders(value: unknown, source: string): SyncProvider[];` (no file stated).
  - Evidence: `packages/pangolin-cli/src/providers/index.ts` today holds the built-in registry (`:11-14`), `resolveProvider` (`:16-23`), `listProviderNames` (`:25-27`), and the type re-exports (`:29`). §3 enumerates only three *additions* to the public surface (`ClaudeCodeProvider`, `StoaProvider`, `splitFrontmatter`) but the subpath publishes the whole module, so `resolveProvider`, `mergeProviders`, and `listProviderNames` ship as public API too. `listProviderNames` is dead in-tree — zero callers by two searches (repo-wide symbol grep → only `providers/index.ts:25`; enumeration of every importer of the barrel → `cmd-subagent.ts:20` and `cmd-capabilities.ts:21`, both importing `resolveProvider` alone) — yet §4.3 widens its signature and D1 publishes it.
  - Concrete failure: no crash. Two costs. (1) D7 commits to a "provisional" SPI but nothing in the spec says *which* exports are the SPI, so a third party binding to `mergeProviders(extra)` is, on the text as written, an equally supported consumer of the published subpath — and the §9 "Exports" test ("`./providers` resolves types and values") will lock in whatever is there. (2) SRP: `providers/index.ts` acquires a fourth and fifth reason to change (built-in registry membership, merge/collision policy, third-party shape validation, public-barrel contents, subpath stability) in the same file the spec is making the package's second published entry point.
  - Resolution: split before publishing — move `PROVIDERS`, `resolveProvider`, `listProviderNames`, `mergeProviders`, and `validateSyncProviders` into an internal `src/providers/registry.ts` (cmd-* import from there), and leave `src/providers/index.ts` as a pure barrel exporting exactly the SPI: the three types plus `ClaudeCodeProvider`, `StoaProvider`, `splitFrontmatter`. If the author instead wants the registry functions public, §3 should say so explicitly and §8's provisional note should cover them. Either way, drop the `extra?` parameter from `listProviderNames` until something calls it.

- **DEFERRED** · The shape guard is placed in the config-loading layer rather than at the choke point that consumes the shape, so two paths bypass it and reinstate exactly the `TypeError` §5 exists to prevent.
  - Artifact text: D5 "Config-supplied providers are shape-validated at runtime before use"; §5 "A validator runs before merge" and `validateSyncProviders(value: unknown, source: string)`; §4.3 `resolveProvider(name: string, extra?: readonly SyncProvider[])` and `CliContext` "gains a third seam … `getSyncProviders: () => Promise<SyncProvider[]>`".
  - Evidence: the `source: string` parameter and the requirement that "Errors name the config file and the offending array index" (§5) place the call inside the config loader (`defaultGetSyncProviders`), not inside `mergeProviders`. But `getSyncProviders` is a `CliContext` seam, and `CliContext` is an injected interface with multiple construction sites — `packages/pangolin-cli/src/index.ts:110` (the bin, which would use the validated default) plus `test/integration.test.ts:106-113`, `test/cmd-orch.test.ts:80-84`, `test/cmd-orch-schedule.test.ts:66-70`, `test/cmd-verify.test.ts:123-127`, `test/e2e/manifest-deploy.test.ts:189`. Separately, D1 publishes `resolveProvider(name, extra)` at the `./providers` subpath, where a third party can hand it an unvalidated array directly.
  - Concrete failure: on either bypass path the failure §5 names verbatim — `TypeError: provider.loadSubagents is not a function` surfacing "later … inside a command action" (`cmd-subagent.ts:124`, `cmd-capabilities.ts:59`) — comes straight back, and now without even a config filename to blame, because the guard is upstream of the seam rather than on it.
  - Resolution: fold the shape check into `mergeProviders`, which is the single point both paths pass through (§4.2: "Both delegate to `mergeProviders`"), and keep `validateSyncProviders(value, source)` as the loader-side wrapper that adds the config filename and array index to the message. At minimum, §5 must name the call site — as written it does not, which is what makes the bypass reachable.

- **DEFERRED** · The new provider-resolution prologue is duplicated across both `sync` actions, in a package that already factored this exact concern into a shared helper.
  - Artifact text: "The two `sync` actions (`cmd-subagent.ts:121-135`, `cmd-capabilities.ts:56-70`) await it and pass the result to `resolveProvider`. Everything downstream is untouched — both actions are already the same four steps (resolve → pick dir → load → `runSync` with a register callback, `sync.ts:25`)."
  - Evidence: the spec correctly identifies the two actions as structurally identical, then adds a second identical line to each rather than lifting the shared shape. Prior art for lifting it is in the same package and states the intent explicitly: `packages/pangolin-cli/src/sync.ts:1-7` — "This helper captures that loop once so the cmd-* call sites stay thin and any output-format change … lives in exactly one place." The only per-call variation is `defaultSubagentDir` vs `defaultCapabilityDir` (`cmd-subagent.ts:123` / `cmd-capabilities.ts:58`), the loader method, and the register callback — all parameterizable, which `runSync`'s own `RunSyncOpts` shape (`sync.ts:14-23`) already demonstrates.
  - Concrete failure: none that will break a build — both copies live in one package with a shared import path available, which is precisely the case my brief classifies as DEFERRED. The cost is that the validate/merge/resolve ordering (F3) now has to be kept correct in two hand-written call sites instead of one, in the two commands that terminate in the privileged `subagent.register()` / `capabilities.register()` calls (`cmd-subagent.ts:131`, `cmd-capabilities.ts:66`).
  - Resolution: extend `sync.ts` with a `runProviderSync({ ctx, kind, providerName, from, dryRun, load, register })` that owns `getSyncProviders → resolveProvider → default dir → load → runSync`, leaving each cmd-* action as commander wiring only — which is the split `providers/types.ts:9-15` already declares as the design ("Commander wiring + registration UX in cmd-* files (one concern)").

- **DEFERRED** · One of the three value exports the SPI ships for "composition" is unusable by the sole motivating consumer, per the spec's own §1.1.
  - Artifact text: §3 — "`splitFrontmatter` (re-exported from `../frontmatter.js`) — the other helper every provider reaches for". §1.1 — "Remora also differs in separator convention (bare `\n---\n`, so `splitFrontmatter`'s YAML path does not apply)".
  - Evidence: `packages/pangolin-cli/src/frontmatter.ts:15-21` matches `/^---\r?\n([\s\S]*?)\r?\n---\r?\n?([\s\S]*)$/` and **throws** `no YAML frontmatter found` on anything else, so a bare `\n---\n` file cannot use it at all. Nor can remora compose `ClaudeCodeProvider.loadSubagents`, which hardcodes `{ name, systemPrompt: body }` (`claude-code.ts:43`) — the spec says so at §1.1. Of the three value exports, only `ClaudeCodeProvider.loadCapabilities` (the SKILL.md walk, `claude-code.ts:50-72`) is actually reachable for the one known consumer, and only if remora's `capabilities/` layout uses SKILL.md markers — which §1.1 does not state.
  - Concrete failure: none at build or run time. The risk is scope: a provisional public surface (D7) is being sized by generic reasoning ("every provider reaches for") rather than by the one real consumer, which is the inverse of the discipline §9 applies to documentation ("Only surface landing in this change is listed").
  - Resolution: either state in §3 which export each of remora's four differences (§1.1) actually consumes — that would justify the set from evidence rather than intuition — or narrow the initial export set to `ClaudeCodeProvider` + `StoaProvider` + the types, and add `splitFrontmatter` when a consumer needs it. Adding an export later is non-breaking; removing one from a published subpath is not.

### Checked, no finding

- **Exporting `ClaudeCodeProvider` as a value is genuine reuse-over-reinvent, correctly argued.** Verified both ends: `StoaProvider` holds an instance (`stoa.ts:36`) and delegates wholesale (`:79-81`), and the walk an out-of-tree provider would otherwise duplicate is real and substantial (`claude-code.ts:50-72` plus `dedupeByContent`/`hashFiles`/`findSkillDirs`/`walkInto` at `:90-177`). The composition-over-inheritance framing matches the guidance already published at `docs-site/src/content/docs/how-to/sync-capabilities-subagents.md:156-158`.
- **The hand-rolled `validateSyncProviders` does not reinvent anything available.** `pangolin-cli` has no schema library — deps are `commander` and `yaml` only (`package.json:35-42`); `zod` exists solely in `pangolin-orchestrator`. The in-package idiom for exactly this job is inline `typeof` checks with a `pangolin-cli: …` prefix, at `manifest-parser.ts:33-90`. Matching it is the right call.
- **`SyncProvider[]` over a keyed `Map` (§4.1) is sound.** `name` is `readonly` on the interface (`providers/types.ts:40`); a map key would be a second, divergeable source of truth for the same value. Correct DRY reasoning.
- **D3 (collision = hard error, no shadowing) is sound.** A precedence rule would make "which implementation is `claude-code`" depend on load order at two sites; a hard error keeps one answer. Terminating in `subagent.register()` (`cmd-subagent.ts:131`) / `capabilities.register()` (`cmd-capabilities.ts:66`) makes silent override the wrong default.
- **Widening `CliContext` with a required third seam is not a defect here.** I checked every construction site — `src/index.ts:110`, `test/integration.test.ts:106-113`, `test/cmd-orch.test.ts:80-84` and `:804-810`, `test/cmd-orch-schedule.test.ts:66-70`, `test/cmd-verify.test.ts:123-127`, `test/e2e/manifest-deploy.test.ts:189` — and the repo already established this exact pattern with `getOrchContext` (`src/index.ts:29`), including the fabricated stubs (`integration.test.ts:108-112`, whose comment says so outright). It also cannot break CI: `packages/pangolin-cli/tsconfig.json` includes `src/**/*` only, and the package defines no `typecheck:test` script, so `pnpm -r typecheck` (`.github/workflows/typecheck.yml:44`) never type-checks those literals.
- **§11's exclusions each check out.** The deploy path really is provider-free and already expressive (`manifest-parser.ts:70` accepts either prompt field). The capability bundle path really is provider-owned (`claude-code.ts:66`, with the bundle typed `Record<string, Uint8Array>` at `types.ts:35`). The runtime-adapter loader (`pangolin-worker/src/adapter-loader.ts:25-72`) is a genuinely different loading model in a different package — correctly not a reuse candidate.
- **`resolveProvider` staying synchronous (D4) is the right seam split** — async config I/O stays in the loader, the registry stays pure. Note only that D4's wording ("the merged set is passed in") does not match §4.3's signature (the *extras* are passed in and `mergeProviders` runs inside); harmless, but the two sentences disagree.
- **Adding an `exports` map is the first in this repo** (no package.json under root, `packages/*`, `examples/*`, `deploy/*`, or `docs-site` declares one — verified by two independent sweeps). The `types` + `default` two-condition shape is appropriate for a CJS-emitting package, the `"."` entry is correctly flagged as mandatory in §3, and no repo tooling reads `exports` (`scripts/check-declared-deps.mjs` reads only `dependencies`/`peerDependencies`/`optionalDependencies` and walks `dist`). Nothing in my lens objects.

### Out of lens

- The `main`/`types` fields are retained alongside `exports` (§3) while the package emits CommonJS (no `"type": "module"`; confirmed by the `require.main === module` guard at `src/index.ts:104-109`) — whether an ESM `pangolin.config.mjs` can do `import { ClaudeCodeProvider } from '@quarry-systems/pangolin-cli/providers'` depends on cjs-module-lexer detecting tsc's re-export emit, which no lens here has tested.
- `docs-site/.../reference/package-map.md:8` says "sixteen packages" and lists sixteen, but `:34-36` already carries a note that the README's "six MCP tools" count is stale at nine — worth one line that ADR-0005's enforcement described at spec §1.4 as "exactly six run-time names" may itself be quoting the stale figure.
