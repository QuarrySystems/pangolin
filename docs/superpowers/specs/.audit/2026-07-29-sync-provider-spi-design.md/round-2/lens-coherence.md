### Findings

- **BLOCKING** · §4.2's illustrative lazy-resolve snippet calls `resolveProvider` with 2 arguments; §4.4 declares it as a 3-parameter function with no default for the third.
  - Artifact text (§4.2, line 264–266): "```ts\nconst provider =\n  findBuiltIn(opts.provider) ??\n  resolveProvider(opts.provider, await ctx.getSyncProviders());\n```"
  - Artifact text (§4.4, line 322): "`export function resolveProvider(name: string, extra: readonly unknown[], source: string): SyncProvider;`"
  - §4.6 (line 367) asserts these are not loosely related: "The two-line resolve in §4.2 is **identical** in both actions" — i.e., this is presented as real call-site code, not paraphrase, and §4.3 (line 300) establishes why `source` is required at all: "`source` is the config filename, so the errors below can name it."
  - Concrete failure: a call with 2 arguments against a 3-required-parameter signature with no default is a TypeScript compile error ("Expected 3 arguments, but got 2"). An implementer transcribing §4.2's snippet literally cannot build. Separately, no source in the entire document shows where a literal `source` string (e.g., the resolved config filename) would come from at this call site, since `ctx.getSyncProviders(): Promise<SyncProvider[]>` (§4.5) returns only the provider array, not the filename — so even fixing the arity requires the author to decide where `source` is threaded from.
  - Resolution: undecided as written — author must choose between (a) showing `source` threaded into the §4.2 snippet (and specifying where it comes from, since `getSyncProviders()`'s declared return type carries no filename), or (b) stating explicitly that §4.2's snippet is simplified/pre-consolidation pseudocode and that the literal, correct call only exists after §4.6's `resolveProviderLazily` wrapper — in which case §4.6's "identical" claim needs softening so it doesn't imply the 2-arg version is real code.

- **BLOCKING** · §3.2's `providers/registry.ts` contents table names a `validateSyncProviders` export that contradicts D6's explicit "not a separate pass" architecture and is never defined or used anywhere else in the document.
  - Artifact text (§3.2, line 205): "`providers/registry.ts` *(new)* | `PROVIDERS`, `findBuiltIn`, `resolveProvider`, `mergeProviders`, `validateSyncProviders` | internal — imported by `cmd-*` and `src/index.ts` only"
  - Artifact text (D6, line 157 and §5, lines 399–402): "Config-supplied providers are shape-validated inside `mergeProviders`, the one point every path crosses" and "Validation lives **inside `mergeProviders`** (D6) rather than in a separate pass. That is the one point both the `CliContext` seam and the published `resolveProvider` cross, so 'shape-validated before use' holds on every path rather than only the one that remembers to call a validator."
  - `validateSyncProviders` appears exactly once in the entire document (grep-confirmed with two independent passes: a literal-string grep for `validateSyncProviders`, and a broader case-insensitive grep for `validate`, both returning only line 205 and the unrelated D6/line-401/line-415 prose uses of the word "validate(d)"). It has no declared signature (unlike its table-mates: `findBuiltIn` and `resolveProvider` are typed in §4.4, `mergeProviders` in §4.3, `PROVIDERS` is described in §1.2), no described caller, and no corresponding row in §9's Testing table (all five Validation rows there test `mergeProviders`'/config-load behavior, none names `validateSyncProviders`).
  - Concrete failure: §3.2 explicitly frames its table's "Contents" column as authoritative ("`providers/index.ts` currently mixes the registry with the type barrel... `providers/registry.ts` (new) | Contents |"), and §3.2's header is tagged "(D8)" — a settled decision. An implementer following the table would create an export whose purpose, signature, and caller are unspecified, and whose mere existence as a standalone "separate pass" contradicts D6's stated rationale for folding validation into `mergeProviders` in the first place (this is very likely a leftover from the pre-rewrite draft that round 1's JR3 — "validation folded into `mergeProviders`" — was supposed to have scrubbed everywhere; the fold reached §5 but was not carried through to this table cell).
  - Resolution: undecided as written — author must choose between (a) deleting `validateSyncProviders` from the §3.2 table (matching D6/§5 exactly), or (b) if it is meant to be a private helper `mergeProviders` delegates to, saying so explicitly and reconciling the wording with "rather than in a separate pass" (which currently reads as ruling out exactly this).

- **DEFERRED** · `CliContext.getSyncProviders`'s declared return type (`Promise<SyncProvider[]>`, §4.5) says the data is already validated by the time it leaves the seam; §5/D6's "one point every path crosses" claim and §4.6's `getExtra: () => Promise<readonly unknown[]>` both say it isn't yet.
  - Artifact text (§4.5, line 341): "`getSyncProviders: () => Promise<SyncProvider[]>;`"
  - Artifact text (§4.6, line 374): "`getExtra: () => Promise<readonly unknown[]>,`" — the parameter that receives (per §4.6's framing of consolidating §4.2's two-line resolve) whatever `ctx.getSyncProviders()` would have supplied.
  - Artifact text (§5, lines 399–401): "Validation lives **inside `mergeProviders`**... That is the one point both the `CliContext` seam and the published `resolveProvider` cross" — i.e., the `CliContext` seam's output is asserted to still need validation at `mergeProviders`, which is inconsistent with typing it as already-`SyncProvider[]`.
  - Concrete failure: within this spec's own described call sites, `ctx.getSyncProviders()`'s output is always immediately handed to `resolveProvider`/`mergeProviders` before use, so the mistyped seam causes no observed failure in the flows this document describes — hence DEFERRED rather than BLOCKING. But the type is not honest about validation timing, and a future caller of the published `getSyncProviders` seam that trusts `SyncProvider[]` without routing through `mergeProviders` would get exactly the `TypeError: provider.loadSubagents is not a function` failure §5 exists to prevent, with the type system offering no warning.
  - Resolution: retype `getSyncProviders` (and any place it is threaded, e.g. as `resolveProviderLazily`'s `getExtra`) as `Promise<readonly unknown[]>` to match `resolveProvider`'s/`mergeProviders`'s `extra` parameter and to make D6's "one point" claim literally true of the seam's output type, or explicitly state that `defaultGetSyncProviders` performs its own pre-validation (in which case D6/§5's "the one point every path crosses" needs to name two points).
