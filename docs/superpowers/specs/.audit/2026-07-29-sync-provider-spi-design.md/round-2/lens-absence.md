### Findings

- **BLOCKING** · §4.2's stated blast radius for a broken config is understated in two independent directions, and the spec never states anywhere that a provider module's import-time code executes inside the `pangolin-mcp` server process.
  - Artifact text: §4.2 — "**Consequence for a broken config, accepted deliberately.** A config that throws on import breaks only the invocations that need it. `--provider remora` surfaces the real import error; `--provider claude-code` keeps working and stays silent." The registration form this consequence is accepted *for* is §4.1 — "`import { RemoraProvider } from 'remora-pangolin-provider';` / `export const syncProviders = [new RemoraProvider()];`".
  - Evidence:
    - **Leg A — the MCP server.** `packages/pangolin-mcp/src/bin.ts:21-28` runs the same `['pangolin.config.ts','pangolin.config.js','pangolin.config.mjs']` probe against `process.cwd()` and `await import()`s the whole module; `:53-58` invokes that unconditionally at startup and `console.error(err); process.exit(1)` on any rejection. Both ends checked: producer = §4.1's config example, consumer = `bin.ts:28`. The spec knows this — §1.4 says so verbatim, citing `bin.ts:14-49` and `:53-58` — and §4.2 then reasons as if it did not.
    - **Leg B — non-dry-run built-ins.** `packages/pangolin-cli/src/cmd-subagent.ts:125` (`const client = opts.dryRun ? null : await ctx.getClient();`) and `cmd-capabilities.ts:60` route straight into `defaultGetClient`, which `await import()`s the config at `src/index.ts:59`. So `--provider claude-code` does **not** "keep working" against a throwing config unless `--dry-run` is also passed — the qualifier §4.2 omits. §9's only import-hostile row (`"--provider claude-code --dry-run still succeeds"`) pins the true half and leaves the false half untested.
    - **The absence proper.** No requirement that a provider module be import-safe exists anywhere in the spec (two search strategies in the grounding table). §5 explicitly disclaims behavioral checks ("the validator checks shape, not behavior"), §11 has no row for it, and §10's five documentation bullets carry only a `config.md` note "that two processes import this file" — a reference-doc line, not a constraint stated to the provider author in the authoring guide the spec is rewriting.
  - Concrete failure: `remora-pangolin-provider` is a dependency of the deploy repo, imported at the top of `pangolin.config.mjs` per §4.1. If it fails to import from the cwd the MCP server is launched in — a pruned production install, a `devDependencies`-only placement, a native binding, or any top-level throw — `pangolin-mcp` prints a raw `ERR_MODULE_NOT_FOUND` and exits 1 at startup, for a feature (`sync`) the MCP server does not expose at all. Provider authors are given no reason to keep their module body inert, and the spec has told the reader the opposite scoping. Independently, an operator on a throwing config who reads §4.2 will expect `pangolin subagent sync --provider claude-code` to succeed; it will not.
  - Resolution: correct §4.2 to state the real scope — "a config that throws on import breaks every invocation that constructs a client, plus `pangolin-mcp` startup; only built-in `--dry-run` survives" — and add an import-safety requirement for provider modules to §10's authoring-guide bullets (not just to `config.md`), plus a §9 row for the non-dry-run built-in case.

- **BLOCKING** · §5 justifies not validating provider *output* by naming three downstream guards; one of the three — credential scanning — does not fire on the sync path at all, and the spec's own citation range does not cover it.
  - Artifact text: §5 — "Downstream guards are real, though, and this spec deliberately stays silent on them: a `SubagentDef` with neither prompt field throws (`pangolin-client/src/subagent-register.ts:59-63`), names are segment-checked (`pangolin-core/src/uri.ts:106`), and bundles are size-capped and **credential-scanned** (`pangolin-client/src/capabilities-register.ts:39,71-80`)."
  - Evidence: `pangolin-client/src/capabilities-register.ts:84-88` wraps `assertNoCredentialPattern` in `if (typeof contents === 'string')`. The source's own header states it: `:9-11` — "Binary inputs (`Uint8Array`) are not scanned — the scanner is text-only by contract." The sync path never produces strings: `CapabilityBundle.files` is typed `Record<string, Uint8Array>` (`pangolin-cli/src/providers/types.ts:35`), and `cmd-capabilities.ts:66` passes that bundle through unchanged. (The manual path is the same — `readDirAsBundle` does `out[rel] = await readFile(full)` at `cmd-capabilities.ts:87`, i.e. Buffers.) Negative claim verified two ways: (1) symbol grep for `assertNoCredentialPattern` across `**/src/**/*.ts` returns exactly two call sites — `env-register.ts:111` (string values, fires) and `capabilities-register.ts:85` (string-gated, never fires here); (2) reading the type of the value that reaches it. Note the spec's cited range `:71-80` stops at the size loop and does not include `:84-88`, so the citation never showed the gate. The size cap (`:80-82`) and both other named guards **are** real on this path — verified in the grounding table.
  - Concrete failure: an out-of-tree provider (or a built-in) that bundles a directory containing an `.env`, `credentials`, or key file registers it into durable storage and thence to workers with no credential scan whatsoever. More immediately for this change: §5's stated reason for the validator checking shape-only is void for one third of its support, and per the spec's own rule "§10 (documentation) may only describe surface that lands in the same change", the false claim is on track to be written into the provider-authoring guide as a safety assurance.
  - Resolution: strike "credential-scanned" from §5 or replace it with the accurate statement — "the credential scanner is text-only (`capabilities-register.ts:9-11,84-88`) and does not run on provider-supplied `Uint8Array` bundles; the size cap and the two subagent-side guards do apply." **Downgrade lever for the reconciler:** the hole is pre-existing and equally present on the sibling manual path (`pangolin capabilities register --from <dir>`), which is exactly the "not a new hazard" argument §11 already makes for bundle keys. If the reconciler reads §5 as descriptive prose rather than load-bearing justification, DEFERRED is defensible — but the sentence cannot survive into docs as written.

- **DEFERRED** · The `source: string` parameter threaded through three new signatures has no stated provenance, and the declared `getSyncProviders` seam cannot supply it.
  - Artifact text: §4.3 `mergeProviders(extra: readonly unknown[], source: string)` — "`source` is the config filename, so the errors below can name it"; §4.4 `resolveProvider(name, extra, source)`; §4.6 `resolveProviderLazily(name, getExtra, source)`; §4.5 `getSyncProviders: () => Promise<SyncProvider[]>`.
  - Evidence: the seam returns only the array — the filename the loader actually matched is discarded. The loader picks the first of three candidates (`packages/pangolin-cli/src/index.ts:52`, mirrored at `pangolin-mcp/src/bin.ts:21`), and §7's new `loadConfigModule()` is the only thing that knows which one won (it returns `{ mod, filename }`), but `getSyncProviders` does not surface it. The call sites that must pass `source` are the two command actions (`cmd-subagent.ts:122`, `cmd-capabilities.ts:57`), which have no access to it. The spec also never states `source`'s value in the no-config case, which §6 makes a first-class outcome.
  - Concrete failure: the implementer hardcodes a literal at the two action sites. §5 says every config in the repo is `.mjs` (seven of them); a hardcoded `'pangolin.config.ts'` — the first resolution candidate, and the one `config.md:18` documents first — names a file that does not exist in any of them, sending the operator to create a second config rather than fix the one they have. §9's row ("the message contains the name, the config filename, and the entry index") is written from the spec and passes against whatever literal is chosen.
  - Resolution: state it — either widen the seam to `() => Promise<{ providers: unknown[]; source: string }>`, or specify that `source` is the filename returned by `loadConfigModule()` and that `getSyncProviders` must carry it out.

- **DEFERRED** · The spec never enumerates which invocations now perform config I/O, so two newly-config-loading paths go unstated and untested: `--dry-run` with a config-supplied provider, and a mistyped `--provider`.
  - Artifact text: §4.2 — "This preserves the property that `--dry-run` performs no config I/O. That property is load-bearing". §4.4 — "Its unknown-provider error (`providers/index.ts:20`) enumerates config providers too".
  - Evidence: under §4.2's `findBuiltIn(name) ?? resolveProvider(name, await ctx.getSyncProviders())`, *any* built-in miss loads the config — including `--provider remora --dry-run` and including `--provider claude-cod` (typo). Config bodies are not inert, as the spec itself establishes: `examples/offload-fanout/pangolin.config.mjs:63` opens a SQLite file and `:66` registers a `process.on('exit')` hook (verified); `deploy/serve-stack/pangolin.config.mjs:26` constructs a live `PangolinClient` with credential providers. §9's three laziness rows cover built-in-no-call, config-provider-does-call, and import-hostile-plus-built-in-dry-run; none covers config-provider dry-run, and none covers a typo.
  - Concrete failure: (a) the stated invariant "`--dry-run` performs no config I/O" silently narrows to "`--dry-run` on a built-in", so a user previewing an out-of-tree provider takes a SQLite file lock and an exit hook they did not ask for, with nothing in the suite pinning the narrowing; (b) a typo'd built-in name in a repo with a throwing config now reports the module-resolution error instead of `unknown --provider 'claude-cod' (known: claude-code, stoa)` — the discoverability affordance §4.4 is built around, lost precisely when the user needs it.
  - Resolution: replace the absolute invariant with the scoped one and enumerate the config-loading invocation set explicitly; add a §9 row for config-provider `--dry-run` and one for a typo'd name against a present config.

- **DEFERRED** · §4.5 accounts for the one production `CliContext` construction site and is silent on the in-repo test fixtures that construct it, one of which breaks.
  - Artifact text: §4.5 — "**The sole real construction site is `index.ts:110`** … The member is **required**, not optional." §9's wiring row drives `buildProgram({ getClient, getOrchContext, getSyncProviders })`. No text or test row addresses existing constructors.
  - Evidence: `packages/pangolin-cli/test/cmd-subagent.test.ts:124-132` — `attachSubagentCmd(program, { getClient: async () => ({} as any) })` then asserts `.rejects.toThrow(/unknown --provider 'made-up'/)`. `made-up` is a built-in miss, so §4.2's resolve invokes `ctx.getSyncProviders()`, which is `undefined` in that fixture → `TypeError: ctx.getSyncProviders is not a function`, and the regex assertion fails. Per the charter's enforcement map, `pangolin-cli` has no `tsconfig.test.json` and `tsconfig.json` is `"include": ["src/**/*"]`, so this is not a compile error — it is a runtime test failure. (The other fixtures survive: lazy resolution means the built-in tests at `cmd-subagent.test.ts:92,114` and `cmd-capabilities.test.ts:36,60` never reach the seam, and `test/bin-entry.test.ts:5` already omits the existing required `getOrchContext` without consequence.)
  - Concrete failure: the change lands red on a test the implementer did not expect to touch, and the shortest green path is to weaken that assertion or make the member optional — which §4.5 forbids. Round 1's resolution ("state that all `CliContext` constructors are updated") was applied only to `index.ts:110`.
  - Resolution: add one line to §4.5 naming `test/cmd-subagent.test.ts:124-132` as the one existing fixture that must gain `getSyncProviders`, and why the others need not.

### Checked, no finding

- **The §3.3 "Known risk" blast radius for the `exports` map is accurately stated, not understated.** Verified two ways (grounding table). Additionally: the repo is `moduleResolution: NodeNext` throughout (`tsconfig.base.json`), so `exports` is honored in-repo and any breakage would surface at build; `bin` is `dist/index.js` resolved by path (`package.json:25-27`), unaffected; `test/scaffold-shape.test.ts:23-61` asserts individual keys, never an exhaustive key set, so adding `exports` trips nothing. Nothing in the repo resolves `@quarry-systems/pangolin-cli/package.json`, so the missing `"./package.json"` subpath costs nothing here.
- **Idempotency and replay of a repeated sync.** Correct silence. `registerSubagent` short-circuits on matching content hash (`subagent-register.ts:97-101`) and `registerCapability` likewise (`capabilities-register.ts:19-23`); running `sync` twice is a no-op write. The SPI changes nothing about it.
- **Double evaluation of the config body.** `defaultGetClient` and a new `defaultGetSyncProviders` both `await import()` the same resolved file URL in one process; the ESM registry caches by URL, so the module body — SQLite handle and exit hook included — evaluates once. No memoization is needed on `loadConfigModule` for correctness, and none is implied.
- **Empty and boundary inputs on the new export.** `syncProviders = []` merges to built-ins-only; `undefined`, `null`, non-array, non-object entry, missing method, and non-string `name` are all enumerated in §5's ordered check list. Zero-item `loadSubagents` output prints nothing and exits 0 — pre-existing `runSync` behavior (`sync.ts:26`), unchanged.
- **Ordering and tie-breaking.** §4.4 pins a unique deterministic key for the enumeration (Map insertion order, built-ins first), matching `providers/index.ts:11-14`. `runSync` is a sequential single-process loop (`sync.ts:26-33`).
- **Timezone/date, migration/backfill, cross-tenant scope.** Nothing in this change crosses a date boundary or adds a persisted field needing backfill. Provider output cannot cross namespaces — `client.namespace` is bound by the caller at `subagent-register.ts:83`, not by the provider.
- **Arbitrary bundle keys are not a new hazard.** §11's dismissal holds: bundle keys are provider-owned `relative()` paths (`cmd-capabilities.ts:86`) and the same keys are reachable today via `capabilities register --from <dir>`.
- **CI ordering for the §9 `require.resolve`-against-`dist` rows.** `.github/workflows/ci.yml:59-60` builds immediately before test, so those rows can observe real build output in CI. (Locally `pnpm -r test` does not build first — the charter's third verification gotcha — but that is a pre-existing property of every suite, not an absence in this spec.)
