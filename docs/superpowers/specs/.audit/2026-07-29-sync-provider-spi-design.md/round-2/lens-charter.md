### Findings

- **DEFERRED** · Charter enforcement-map row "Workspace dep cycles | `pnpm run check:deps` (`ci.yml:53`)" mischaracterizes what that check does — the code wins, this charter row is stale.
  - Charter text: "| Workspace dep cycles | `pnpm run check:deps` (`ci.yml:53`) | CI failure |"
  - Evidence: `scripts/check-declared-deps.mjs:1-108` is a "clean-room dependency guard" — for every package's built `dist/`, it asserts each bare import specifier is either a Node builtin or a *declared* dependency in that package's `package.json` (catching the undeclared/phantom-hoist class, per the script's own header comment at `:2-13`). It contains no graph-traversal or cycle-detection logic. Two independent searches confirm there is no separate cycle checker anywhere in the repo: (1) `grep -rn "cycle" package.json scripts/*.mjs .github/workflows/*.yml pnpm-workspace.yaml` returns nothing relevant (one unrelated hit for "lifecycle" in an unrelated workflow file); (2) reading both `.github/workflows/dep-allowlist.yml` and its script `scripts/check-dep-allowlist.mjs` shows that job is a *different* check — an external-library-prefix allowlist ("orthogonality boundary," §7.7), also not a cycle detector.
  - Concrete failure for this spec: none. The spec's own D10 reasoning (declining to share the config loader with `pangolin-mcp`) is grounded in `package-map.md`'s documented dependency graph, not in cycle-detection tooling, and adding the `mcp --> cli` edge the spec declines to add would not, in fact, create a cycle (neither package currently depends on the other in either direction) — so this charter error doesn't change any verdict on the spec. It is reported per the charter's own rule that a stale entry is worth flagging, and per this round's explicit charge to verify the charter's claims against the code.
  - Resolution: retitle that enforcement-map row to describe what `check:deps` actually checks (undeclared/phantom dependencies in built output), and either remove the "workspace dep cycles" claim or note that no such check currently exists in this repo.

- **DEFERRED** · §4.5's own detectability story for the new required `CliContext.getSyncProviders` member is imprecise about which typecheck gate is powerless, in both directions — it understates protection at the one site it names, and doesn't mention a parallel gap it doesn't name.
  - Artifact text (§4.5): "This is called out explicitly because nothing currently catches its omission: `test/bin-entry.test.ts:5-7` builds its own stub and never parses argv, no test in `test/e2e/` spawns the `pangolin` bin, and `tsconfig.json` sets `"include": ["src/**/*"]` with no `typecheck:test` script — so a missing member would ship as a runtime `TypeError` with `test`, `lint`, and `typecheck` all green." Two sentences later: "The member is **required**, not optional."
  - Evidence, part A (the claim overstates the risk at the cited site): `CliContext` is defined at `packages/pangolin-cli/src/index.ts:23-30` and its sole construction site is `index.ts:110`, in the *same file*, which is covered by `tsc --noEmit` under `tsconfig.json:7`'s `"include": ["src/**/*"]`. Once `getSyncProviders` is a non-optional interface member, TypeScript's structural-assignability check (not the excess-property/"freshness" check the spec's "include" citation is really about — a *missing* required property is flagged unconditionally, regardless of literal freshness) fails to compile `{ getClient: defaultGetClient, getOrchContext: defaultGetOrchContext }` against a three-member-required `CliContext` the moment line 110 isn't updated. `pnpm -r typecheck` is the enforcement-map's row-1 gate — unconditional, every package, `.github/workflows/typecheck.yml:48-49` — not the opt-in `typecheck:test` row the surrounding sentence is actually describing. So "typecheck ... green" is not accurate for this specific site under the "required, not optional" decision the spec itself makes two sentences later; a bare interface-only edit without the line-110 fix would fail CI at the ordinary `pnpm -r typecheck` step, not ship silently.
  - Evidence, part B (a real, unnamed instance of the gap the spec is trying to describe): the same required-member risk *does* apply, uncaught, to the `CliContext`-typed test fixtures elsewhere in `pangolin-cli`'s own test suite — and this is not hypothetical, it is already true today for the existing two-member interface. `attachCapabilitiesCmd`/`attachSubagentCmd` are typed `ctx: CliContext` (`cmd-capabilities.ts:24`, `cmd-subagent.ts:23`), and `CliContext.getOrchContext` is already non-optional (`index.ts:26-29`, no `?`) — yet `test/cmd-capabilities.test.ts:15,36,60` and `test/cmd-subagent.test.ts:15,32,53,67,92,114,126` call these functions with object literals containing only `{ getClient: ... }`, omitting the already-required `getOrchContext`. This is a live, currently-uncaught type violation, invisible because `pangolin-cli` has no `tsconfig.test.json`/`typecheck:test` (confirmed above). Adding a third required member continues this exact pattern, and §9's 19-row testing table has no row that verifies the existing fixtures were updated to include `getSyncProviders`.
  - Concrete failure: none that changes behavior — part A means the real safety net is *stronger* than described (a loud `pnpm -r typecheck` compile failure at the one site the spec names, not a silent runtime `TypeError`); part B means stale/type-invalid test doubles can accumulate silently in exactly the files this change touches, but D4's laziness design means none of the affected fixtures currently exercise the config-provider path at runtime, so no vitest failure results either — it is pure, permanent type-hygiene rot, consistent with (not novel relative to) the repo's already-accepted, already-tracked ten-package test-typecheck debt (`.eslintrc.cjs:51-54`, "213-error debt tracked in issue #99" — note `.github/workflows/typecheck.yml:53`'s own comment cites the same debt as "issue #103"; the two in-repo citations of the same debt disagree with each other, a small pre-existing inconsistency independent of this spec).
  - Resolution: reword §4.5 to scope the "nothing catches it" claim to the `typecheck:test`/runtime-test gap specifically (not "typecheck" bare), and optionally add one line noting that the `CliContext`-typed fixtures in `test/cmd-*.test.ts` should gain `getSyncProviders` in the same change — not because anything will fail if they don't, but because it's the same class of drift the section is otherwise careful to name.
