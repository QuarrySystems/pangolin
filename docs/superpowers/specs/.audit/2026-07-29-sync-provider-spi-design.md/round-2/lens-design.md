### Findings

- **BLOCKING** · §4.5's caller analysis missed the one existing test that *does* traverse the new seam. As specified, the change lands `pnpm -r test` red, and the cheapest local repair silently reintroduces B2.
  - Artifact text: §4.5 — "**The sole real construction site is `index.ts:110`** … This is called out explicitly because nothing currently catches its omission: `test/bin-entry.test.ts:5-7` builds its own stub and never parses argv, no test in `test/e2e/` spawns the `pangolin` bin … so a missing member would ship as a runtime `TypeError` with `test`, `lint`, and `typecheck` all green." Plus §4.2's snippet: `findBuiltIn(opts.provider) ?? resolveProvider(opts.provider, await ctx.getSyncProviders())`.
  - Evidence: `packages/pangolin-cli/test/cmd-subagent.test.ts:124-132` — `attachSubagentCmd(program, { getClient: async () => ({} as any) })` at `:126` (no `getSyncProviders`), then `parseAsync([... 'sync', '--provider', 'made-up', '--from', '.'])` at `:128-130`, asserting `.rejects.toThrow(/unknown --provider 'made-up'/)` at `:131`. `made-up` is a built-in **miss**, so under §4.2 the right-hand operand of `??` *is* evaluated and `ctx.getSyncProviders()` is called on an object that has no such member. Negative claim — "no other test reaches the config-miss path" — checked two ways: (1) repo-wide grep for `unknown --provider|made-up` (ex-`dist`) returns only `cmd-subagent.test.ts:129,131`; (2) enumerating every `attachSubagentCmd|attachCapabilitiesCmd|buildProgram` construction site and reading its argv — `cmd-subagent.test.ts:94,117` and `cmd-capabilities.test.ts:39,63` all pass `--provider claude-code`, and `bin-entry.test.ts:6` / `integration.test.ts:117` never invoke `sync`. Gate: `.github/workflows/ci.yml:69`.
  - Concrete failure: two, in sequence. (a) **Immediate:** the rejection message becomes `ctx.getSyncProviders is not a function`, which does not match the `:131` regex, so the assertion fails and `pnpm -r --workspace-concurrency=1 test` goes red in CI. §9's 19 rows contain no row for updating this fixture, and §11 does not exclude it. (b) **The design consequence, which is the reason this is not merely bookkeeping:** the seam is reachable from exactly one code path — the built-in miss — and that path is driven only by a test-supplied context. So the red test creates a false detection signal: an implementer can turn it green with a one-line fixture edit and `index.ts:110` remains unwired, with every built-in invocation (the only thing real users run today) still green. Worse, the most natural repair for "the fixture doesn't have this member" is defensive access — `await ctx.getSyncProviders?.() ?? []`, or declaring the member optional — which contradicts §4.5's explicit "The member is **required**, not optional" and its changelog obligation, *and* converts the unwired-`index.ts:110` case from a loud `TypeError` into a silent `[]`. In that state `--provider remora` against a correct config reports `unknown --provider 'remora' (known: claude-code, stoa)` — the SPI simply does not work, with the whole suite green. That is B2 restored in a form the §9 wiring row does not catch, because the wiring row constructs the context correctly by hand.
  - Resolution: add the fixture to the change's scope explicitly — one §9 row or one line in §4.5 naming `cmd-subagent.test.ts:126` as a construction site that must gain `getSyncProviders: async () => []`, and stating that the repair is *widening the fixture*, not making the member optional and not optional-chaining the call. Correct §4.5's "with `test` … green" premise while you are there: `test` does **not** stay green, `lint` and `typecheck` do. Consider also adding the mirror-image test on the capabilities side (`cmd-capabilities.test.ts` has no unknown-provider case at all, so its lazy-resolve path has zero existing coverage) — but that is a testing call, not mine.

- **DEFERRED** · `source` has no route from the component that knows it to the component that needs it; the call site the spec hands it to cannot know its value.
  - Artifact text: §4.3 — "`source` is the config filename, so the errors below can name it"; §4.6 — `resolveProviderLazily(name: string, getExtra: () => Promise<readonly unknown[]>, source: string)`; §4.5 — `getSyncProviders: () => Promise<SyncProvider[]>`; §7 — `loadConfigModule(): Promise<{ mod: Record<string, unknown>; filename: string } | null>`.
  - Evidence: the filename is discovered by the resolution loop and is loop-local — `index.ts:52` (`for (const filename of [...])`) with `filename` interpolated only inside that scope at `:63` and `:88`. §7 keeps it that way (`loadConfigModule` returns it). But the seam that carries values out to the resolver is `CliContext.getSyncProviders`, whose declared return type is `Promise<SyncProvider[]>` — no filename. And `resolveProviderLazily` receives `source` as a *third argument from the caller*, i.e. from the sync action in `cmd-subagent.ts` / `cmd-capabilities.ts`, which has no way to know whether `.ts`, `.js`, or `.mjs` was found — or whether any file was found at all. The chain `resolveProviderLazily → resolveProvider(name, extra, source) → mergeProviders(extra, source)` threads a parameter whose only true producer sits on the far side of `getExtra`.
  - Concrete failure: not a compile error — a hardcoded literal type-checks. The failure is that the error text §4.3/§5/§9 promise ("the message contains the name, the config filename, and the entry index") cannot be produced as designed. The implementer's two realistic outs both cost something the spec did not budget for: hardcoding `'pangolin.config'` at both action call sites puts a *third and fourth* independent statement of the config-file identity into `cmd-subagent.ts` and `cmd-capabilities.ts` — in the same change whose D10 is about collapsing copies of exactly that knowledge — and makes the §9 validation rows assert a string that is not a filename; alternatively widening `getSyncProviders` to `Promise<{ providers; source }>` invalidates §4.5's stated signature and its "breaking change to the root surface" analysis. Secondary SoC note: `source: string` is a config-loader concern, and §4.6 places all three functions that carry it in `providers/registry.ts`, which §3.2 otherwise describes as the pure registry.
  - Resolution: undecidable as written — the author must choose. **(A)** `getSyncProviders: () => Promise<{ providers: readonly unknown[]; source: string }>` (or `null` for "no config"), dropping `source` from `resolveProviderLazily`'s parameter list; the seam then carries the datum with the data, and §4.5's semver note updates once. **(B)** Keep the signatures and state plainly that `source` is a caller-supplied *label*, not the resolved filename, and change §4.3/§5/§9's wording from "the config filename" to that label. (A) is the smaller total edit and keeps the D10 consolidation honest.

- **DEFERRED** · D6's "validation folded into `mergeProviders`" is only half-applied: `validateSyncProviders` survives as a separate named member of `registry.ts`, restoring the second entry point D6 removed.
  - Artifact text: §3.2 table — "`providers/registry.ts` *(new)* | `PROVIDERS`, `findBuiltIn`, `resolveProvider`, `mergeProviders`, **`validateSyncProviders`**". Versus §5 — "Validation lives **inside `mergeProviders`** (D6) rather than in a separate pass. That is the one point both the `CliContext` seam and the published `resolveProvider` cross, so 'shape-validated before use' holds on every path rather than only the one that remembers to call a validator."
  - Evidence: the artifact itself, at the two locations quoted. There is no code to cite — nothing is implemented — but the two statements describe different module surfaces. Round 1's resolution (per the audit record at spec:615-616, "JR3 … validation folded into `mergeProviders`") is what §5 enacts; §3.2's table was written from the pre-resolution shape and was not updated.
  - Concrete failure: none that compiles or crashes — hence DEFERRED. The design cost is that `registry.ts` ends up with five exported members for one operation, one of which (`validateSyncProviders`) has exactly one caller (`mergeProviders`) and exists only as a name an implementer or a later refactor can reach for directly. The invariant §5 buys — "shape-validated before use holds on *every* path" — is an argument about there being one door; leaving a second named door in the surface table is what makes the argument false again the first time someone calls the validator standalone and then merges by hand.
  - Resolution: drop `validateSyncProviders` from §3.2's `registry.ts` row (make it a module-private helper inside `registry.ts`, or inline it), or state in §5 that it remains exported *for tests only* and that `mergeProviders` is the sole production caller. The former matches D6's intent.

### Checked, no finding

- **The `runProviderSync` decline (§4.6) is correctly reasoned — do not revisit.** I traced both actions rather than taking the spec's word: `cmd-subagent.ts:121-135` and `cmd-capabilities.ts:56-70` genuinely differ in all four values the spec names (`defaultSubagentDir` vs `defaultCapabilityDir` at `:123`/`:58`, `loadSubagents` vs `loadCapabilities` at `:124`/`:59`, the `kind` label, and the register callback at `:130-133`/`:65-68`). The only genuinely shared remainder beyond the resolve is the `opts.dryRun ? null : await ctx.getClient()` + `client!` pattern at `:125,131` / `:60,66`, which is two lines and already covered by `runSync` (`sync.ts:25-34`) on the loop side. Extracting `resolveProviderLazily` and stopping there is the right cut.
- **`resolveProviderLazily` taking a `getExtra` callback rather than a `CliContext`** keeps `providers/registry.ts` free of any dependency on `src/index.ts`, so the barrel split introduces no import cycle: `registry.ts` → `./claude-code.js`, `./stoa.js`, `./types.js`; `cmd-*` → `registry.ts`; nothing points back. Verified against the current import graph (`cmd-subagent.ts:20`, `cmd-capabilities.ts:21`, `providers/index.ts:7-9`, `stoa.ts:19`).
- **Hand-rolling shape validation is not reinvention.** `packages/pangolin-cli/src/manifest-parser.ts:37-88` is the same job done the same way (typeof-guard per field, error naming the source path), and `packages/pangolin-cli/package.json:40-41` shows the only runtime deps are `commander` and `yaml` — there is no schema library to reuse. The spec's §5 citation holds.
- **The `exports` map divergence (§3.1) is deliberate and correctly flagged.** Confirmed no other `package.json` in the repo has an `exports` map, by two independent sweeps (per-directory glob on `packages/*/package.json` + `examples/*/package.json`, and a repo-wide `find`-plus-grep excluding `node_modules`). A subpath cannot be declared without one, so the divergence is forced rather than chosen.
- **Leaving copy 3 in `pangolin-mcp` (§7, D10) is the right call, though §7 names an incomplete reason.** §7 argues only that sharing would add a `pangolin-mcp → pangolin-cli` edge. There is in fact a third option it does not consider: both packages already depend on `@quarry-systems/pangolin-core` (`packages/pangolin-cli/package.json:37`, `packages/pangolin-mcp/package.json` deps), so a helper there needs no new edge. I checked it and it is *worse*: `pangolin-core` declares itself "Types-only contract package" (`packages/pangolin-core/package.json:5`) and `package-map.md:16` repeats that as the layering rule, so a cwd-relative filesystem config loader does not belong there. Per my brief, this is the "note the divergence deliberately" case, and §7 already does note it (pointer comments in all three loaders + a `config.md` line). Net effect of D10 is 3 copies → 2, an improvement. No finding; the missing alternative is worth one sentence if the author is editing §7 anyway.
- **Leaving `listProviderNames` alone (§4.4) is right.** Zero callers, verified two ways (symbol grep repo-wide excluding `dist`; and enumerating both barrel importers, which take `resolveProvider` only). Keeping it out of the SPI barrel is consistent with §3.2's narrow-by-default asymmetry.
- **The `SyncProvider[]` array shape over a `Map` (§4.1)** avoids duplicating the `readonly name` that already exists on the interface (`providers/types.ts:40`). Correct DRY call.
- **`splitFrontmatter` in the SPI barrel (§3.2)** — both in-tree providers depend on it (`claude-code.ts:38` via the import at `:23`, `stoa.ts:66` via `:18`), so publishing it is reuse-serving even though the motivating consumer cannot use it (`frontmatter.ts:19-21` throws on the leading-delimiter miss, confirmed at `frontmatter.ts:15`). The spec's own escape hatch ("if that rationale does not hold at implementation time, drop it") is the right posture.
