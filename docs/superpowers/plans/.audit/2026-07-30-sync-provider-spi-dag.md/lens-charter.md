### Findings

- **DEFERRED** · `task-changelog` points at an already-released changelog section as "the existing convention," and following it literally back-dates a not-yet-shipped breaking change into a tagged, published release.
  - Artifact text: "Record the `CliContext` breaking change under the existing `### Breaking` convention... The entry lands under a `### Breaking` heading, matching the existing convention at `CHANGELOG.md:12`." No mention of `[Unreleased]` appears anywhere in the task or in the rest of the plan.
  - Evidence: `CHANGELOG.md:1-18` has **no `## [Unreleased]` section at all** — the file goes directly from the header to `## [0.4.0] - 2026-07-28` (confirmed by a second, independent grep for `## \[` across the whole file: the only headings are `[0.4.0]`, `[0.3.1]`, `[0.3.0]`, `[0.1.0]`). `git tag -l` lists `v0.4.0`, and `git log --format=%H %ad %s -- packages/pangolin-cli/package.json` shows `5c57fe1 2026-07-29 Typed storage not-found: StorageNotFoundError (0.4.0) (#106)` — 0.4.0 is tagged and released, not a placeholder heading. `RELEASING.md` documents "npm versions are immutable" as a first-class hazard (lines 32-45). The immediately preceding same-day sister plan, `docs/superpowers/plans/2026-07-28-storage-not-found-dag.md:997-1002` (`task-release-prep`, `status: done`), shows the actual house convention: the `### Breaking` bullet for *that* change was added to `[Unreleased]` during normal development, and a dedicated, later, `is_wiring_task`-marked release-prep task turned `[Unreleased]` into `## [0.4.0] - 2026-07-28` **at the same time** it bumped all 16 `package.json` versions and tagged the release. That is in fact the origin of the very heading `task-changelog` cites as its model.
  - Concrete failure: if `task-changelog` is implemented as literally described, the new bullet is appended under the `## [0.4.0]` section of an npm release that is already published and immutable. `CHANGELOG.md` would then falsely document that the published `0.4.0` tarballs contain the `CliContext.getSyncProviders` breaking change, when they do not. It also leaves no `[Unreleased]` section for whatever release-prep task eventually ships this work, reproducing — in the changelog rather than a package version — exactly the kind of "looks-fine, is-actually-wrong" state `RELEASING.md` spends a full paragraph warning about for npm publishes.
  - Resolution: `task-changelog` should add a new `## [Unreleased]` heading (with its own `### Breaking` subheading) above `## [0.4.0]`, not append into the existing 0.4.0 section — mirroring the `[Unreleased]` → `## [x.y.z]` promotion pattern `task-release-prep` in the storage-not-found-dag plan already executed for this same section, and that `RELEASING.md:13-15` documents as the intended workflow.
  - Note on grading: nothing in CI validates `CHANGELOG.md` structure (`grep -rn CHANGELOG .github/workflows/*.yml scripts/*.mjs` → zero hits), so per the enforcement rule this stays DEFERRED rather than BLOCKING — but it is a concrete, well-evidenced defect, not a style preference, and the reconciler may weigh it accordingly given how directly the sibling plan demonstrates the correct pattern.

- **DEFERRED** · New provider-registry test files break the established `test/providers/<name>.test.ts` mirroring convention.
  - Artifact text: `task-registry` files: `packages/pangolin-cli/test/providers-registry.test.ts`; `task-barrel` files: `packages/pangolin-cli/test/providers-barrel.test.ts`.
  - Evidence: the package's existing tests for `src/providers/*` already live one level down, mirroring the source layout 1:1 — `packages/pangolin-cli/test/providers/claude-code.test.ts` and `.../test/providers/stoa.test.ts` (confirmed via directory listing). `src/providers/registry.ts` (task-registry's own new file) would be the third file under `src/providers/`, and every existing sibling's test sits at `test/providers/<name>.test.ts`, not flattened into `test/<area>-<name>.test.ts`. No vitest config restricts discovery to a specific subtree (`packages/pangolin-cli/vitest.config.ts` merges only the repo-wide `vitest.shared.js`, which sets only timeouts — no `include` override), so this is a placement/convention deviation, not a functional break.
  - Concrete failure: none functional — `vitest run`'s default glob discovers `test/providers-registry.test.ts` and `test/providers-barrel.test.ts` regardless of directory depth, so `pnpm -r test` and `pnpm -r lint` (which covers `test` with `eslint src test --ext .ts`) both still pass. The cost is purely a same-package inconsistency: a future reader scanning `test/providers/` for "everything that tests `src/providers/*`" will miss two of the four files added under this plan.
  - Resolution: place them at `test/providers/registry.test.ts` and `test/providers/barrel.test.ts` (or `test/providers/index.test.ts`, matching `src/providers/index.ts`) to keep the mirror intact — no functional requirement forces the flatter names used in the plan.

- **DEFERRED** · Scope guard 1's file-count claim is off by one, weakening (without invalidating) the plan's own scope-creep fence.
  - Artifact text: "A grep for `getClient:` finds **44 construction sites across 12 test files**... **The other ten test files are out of scope.**"
  - Evidence: `Grep getClient: packages/pangolin-cli/test` (ripgrep, count mode) returns "44 total occurrences across **11** files" — the 44 figure is correct, the file count is not. `task-actions` touches 2 of those 11 (`cmd-subagent.test.ts`, `cmd-capabilities.test.ts`), leaving 9 out-of-scope files, not 10.
  - Concrete failure: none directly — the two in-scope files are named explicitly by path in `files:`, and `task-actions`'s acceptance criterion ("`grep -c \"getSyncProviders\"` ... counts exactly the two files in this task's `files:`") is self-verifying and doesn't depend on the "ten" figure. The risk is soft: an implementer who re-derives the count while re-reading the scope guard (exactly the check-your-work behavior the guard is trying to induce) gets a number that doesn't match the plan's own text, which can erode trust in the guard at the moment it matters most — deciding whether a given file is "the other nine/ten" or a missed twelfth site.
  - Resolution: correct "12 test files" → "11 test files" and "the other ten" → "the other nine" in both the Context prose and `task-actions`'s acceptance criteria.
