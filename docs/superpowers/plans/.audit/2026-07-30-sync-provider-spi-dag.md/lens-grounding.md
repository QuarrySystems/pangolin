### Findings

- **BLOCKING** · `task-exports`'s out-of-process resolution test cannot pass as written — its probe script is unreachable by design, independent of whether the `exports` map itself is correct.
  - Artifact text: `"const probe = join(await mkdtemp(join(tmpdir(), 'pangolin-spi-')), 'probe.mjs');\nawait writeFile(probe, \`import { ClaudeCodeProvider } from '@quarry-systems/pangolin-cli/providers';\n...\`);\nconst { stdout } = await run(process.execPath, [probe], { cwd: pkgRoot });"` (task-exports, Implementation)
  - Evidence: `mkdtemp(tmpdir())` creates the probe file in an OS temp directory with no `node_modules` ancestor chain related to this repo. Node's ESM resolver for a bare specifier resolves relative to the **importing module's own file location**, walking that file's ancestor directories for `node_modules` — `process.cwd()` (what `{ cwd: pkgRoot }` sets) has no bearing on this at all. Empirically reproduced: a `.mjs` file placed outside the repo and spawned with `cwd` set to `packages/pangolin-cli` (which genuinely has `commander` resolvable) still fails with `ERR_MODULE_NOT_FOUND: Cannot find package 'commander'` — the exact failure class `@quarry-systems/pangolin-cli/providers` would hit. This repo's own precedent already documents the same limitation: `test/e2e/mcp-tool-surface.test.ts:13-18` explains that a root-level test "cannot resolve the bare specifier" and works around it with a **relative path** into the target package's `node_modules`, "matching the convention every other root-level E2E test uses." The plan's probe uses neither a relative path nor a location inside `pkgRoot`.
  - Concrete failure: `await run(...)` rejects (non-zero exit, `ERR_MODULE_NOT_FOUND` on stderr) before printing anything; the unwrapped `await` propagates as an uncaught test failure. The test fails every run, so this acceptance criterion ("A real `.mjs` file, run by node, named-imports `ClaudeCodeProvider` from the subpath") can never be satisfied by this implementation, regardless of whether `package.json`'s `exports` map is correct — the one test meant to pin the entire `./providers` subpath (§3.1's central claim) tests nothing and cannot go green.
  - Resolution: undecided as written — two workable directions: (a) write the probe under a `mkdtemp` **inside `pkgRoot`** (e.g. `mkdtemp(join(pkgRoot, '.tmp-probe-'))`) so Node's native package self-reference algorithm finds `packages/pangolin-cli/package.json` as the nearest ancestor and resolves through its own `exports` map; or (b) mirror `mcp-tool-surface.test.ts`'s workaround and import via a relative path into `packages/pangolin-cli`'s own resolved location rather than the bare specifier. (a) is closer to what the test claims to prove (a real external consumer importing by package name) and is the more likely intended fix.
